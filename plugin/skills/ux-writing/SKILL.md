# UX Writing

화면 안에서 사용자가 다음 행동을 하게 만드는 문구를 씁니다. 산문이 아니라
인터페이스 부품입니다. 짧을수록 좋은 게 아니라 **행동이 분명할수록** 좋습니다.

## 먼저 확인

1. `~/.claude/personal-harness-data/global/DESIGN-TASTE.md`와 프로젝트
   `.harness/DESIGN.md`에 확정된 어체·금지 표현이 있으면 그것이 최우선입니다.
2. 이 문구가 붙는 **컴포넌트 종류**를 확정합니다. 버튼과 토스트와 에러는 서로
   다른 규칙을 씁니다.
3. 사용자가 그 순간 하려던 일, 막힌 지점, 다음에 할 수 있는 행동을 정합니다.
4. 제품 전체의 어체가 이미 있으면 새로 만들지 않고 따릅니다. 없으면 어체를
   먼저 하나 정하고 나머지를 맞춥니다.

기존 화면을 고칠 때는 주변 문구의 어체를 먼저 읽고 그 안에서 고칩니다.
한 화면에 `-해요체`와 `-합니다체`가 섞이는 것이 개별 문장의 어색함보다 더
크게 드러납니다.

## 작성

[references/korean-voice.md](references/korean-voice.md)의 금지·대안 대조표를
적용합니다. 특히 아래 다섯 개는 예외 없이 지웁니다.

- `—` 줄표: 한국어 문장부호가 아닙니다. 쉼표, 콜론, 문장 분리로 바꿉니다
- 과공대: `~하실 수 있습니다`, `~해 주시기 바랍니다`
- 상투구: `성공적으로 완료되었습니다`, `잠시만 기다려 주세요`
- 번역투: `당신의`, `~에 대해`, `~를 통해`, 불필요한 `~들`
- 과장 칭찬과 감탄: `완벽합니다`, `훌륭해요`, 불필요한 느낌표

컴포넌트별 패턴과 문구 길이 기준은
[references/component-copy.md](references/component-copy.md)를 씁니다.

## 산출

문구를 낱개로 주지 않고 **세트로** 줍니다.

| 항목 | 내용 |
|---|---|
| 컴포넌트 | 버튼 / 토스트 / 에러 / 빈 상태 / 다이얼로그 / 폼 |
| 상황 | 사용자가 방금 한 일과 시스템 상태 |
| 문구 | 실제로 넣을 텍스트. 길이 제약이 있으면 글자 수 표기 |
| 어체 | 이 화면에서 쓰는 종결 방식 |
| 다음 행동 | 이 문구가 유도하는 단 하나의 행동 |
| 대안 | 더 짧은 안 또는 더 친절한 안 하나 |

같은 흐름의 문구를 여러 개 만들 때는 상태 전이 순서대로 나열합니다.
`빈 상태 → 로딩 → 성공 → 실패 → 재시도`.

## 어체 결정

- `-해요체`: 소비자 서비스, 온보딩, 격려가 필요한 자리
- `-합니다체`: 금융·의료·계약·관리자 화면, 책임이 걸린 알림
- 명사형 종결: 버튼, 탭, 메뉴, 표 헤더처럼 라벨 성격인 자리.
  단 `-하기` 명사화를 습관으로 붙이지 않습니다. `삭제하기`보다 `삭제`
- 한 화면 안에서 섞지 않습니다. 제품 단위로 하나를 정합니다

## 금지

- 존재하지 않는 기능이나 시점을 문구로 약속하지 않습니다
- 사용자 잘못으로 읽히는 표현을 쓰지 않습니다. 시스템 상태를 서술합니다
- 개발자 용어를 그대로 노출하지 않습니다. `null`, `undefined`, `4xx`, `타임아웃`
- 법적·금융 문구는 임의로 다듬지 않습니다. 준법 검토 대상으로 표시합니다
- 글자 수를 맞추려고 조사나 서술어를 잘라 비문을 만들지 않습니다

## 자체 검토

- 이 문구만 읽고 다음에 무엇을 누를지 알 수 있는가?
- 버튼 라벨이 다이얼로그 본문의 동사와 같은 말인가?
- 에러 문구가 원인과 복구 방법을 함께 주는가?
- 한 화면의 어체가 하나인가?
- `—`, 과공대, 상투구, 번역투, 감탄이 남아 있지 않은가?
- 기존 화면을 고쳤다면 주변 문구와 어체가 어긋나지 않는가?
