# 지식 시스템 구조 결정

- 상태: 채택
- 결정일: 2026-07-29
- 적용 범위: Personal Harness와 하네스를 설치한 프로젝트

## 배경

단일 Markdown 파일만 계속 키우면 사람이 검토하기는 쉽지만 관련 정보를
매 턴 정확히 찾기 어렵습니다. 반대로 DB나 외부 위키만 정본으로 사용하면
이식성, 검토 가능성, 버전 관리가 약해지고 별도 운영 절차가 생깁니다.

## 결정

Markdown을 유일한 정본으로 유지하고 SQLite FTS를 삭제 가능한 검색
인덱스로 사용합니다.

```text
메일·Slack·첨부 → imports 요약 ┐
턴별 질문·답변 → 일일 로그 ────┼→ 검토·승격 → Markdown 정본
현재 상태 → NOW ───────────────┘                │
                                                └→ SQLite FTS 검색 인덱스
```

## 구성

- `PROJECT.md`: 안정적인 배경과 제약
- `NOW.md`: 현재 작업과 다음 행동
- `WIKI.md`: 검증된 지식의 홈과 상세 페이지 색인
- `DESIGN.md`, `MARKETING.md`: 도메인별 정본
- `wiki/**/*.md`: 반복 참조할 결정·방법론·개념
- `logs/`: 자동 생성되는 시간순 증거
- `imports/`: 제한 원본과 조사 요약
- `.index/knowledge.sqlite3`: 언제든 재생성할 수 있는 검색 파생물
- `~/.claude/personal-harness-data/global/`: 프로젝트를 넘는 사용자 프로필과
  디자인 취향의 단일 저장소

## 검색 경계

- 일반 질문: 정본과 전역 선호
- 연속성 질문: 정본 + 일일 로그
- 출처를 명시한 질문: 정본 + 제한 조사 요약
- 첨부 원본과 companion 파일: 인덱싱 제외
- 제한 조사 요약: 검색 결과에 본문을 자동 노출하지 않고 위치만 제공

## 상세 페이지 분리 기준

`WIKI.md`가 500줄을 넘거나, 한 주제가 독립적으로 반복 참조되거나,
담당자·변경 주기가 다를 때만 상세 페이지로 분리합니다. 원래 위치에는
링크와 한 줄 설명만 남기고 내용을 중복하지 않습니다.

## 검증

- 파일 변경 후 검색 결과가 자동 갱신되어야 함
- 일반 검색에서 로그와 imports가 섞이지 않아야 함
- 비밀값·이메일·전화번호가 DB에 원문으로 남지 않아야 함
- 인덱스 디렉터리 `0700`, DB `0600`을 유지해야 함
- 전역 저장소 디렉터리 `0700`, 프로필 파일 `0600`을 유지해야 함
