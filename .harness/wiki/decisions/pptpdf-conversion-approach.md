# ppt/pptx → PDF 변환 방식

- 상태: 채택
- 결정일: 2026-08-06
- 적용 범위: `pptpdf` 스킬 (`plugin/skills/pptpdf/`)

## 결정

ppt/pptx를 PDF로 바꿀 때 LibreOffice 같은 외부 렌더러가 아니라, 이 PC에 설치된
PowerPoint 자체를 COM으로 조작한다. 외부 렌더러는 폰트 메트릭·그림자·그라디언트·
SmartArt 렌더링이 PowerPoint와 미묘하게 달라질 수 있어 "실제 PPT에서 저장한 것과
같다"는 보증을 못 한다.

## 근거

실제 사용자 파일(Wonder ADX 제안서 6개, 최대 320MB)로 변환을 돌려보며 아래를
실측으로 확인했다.

- 이 PC의 Office 빌드는 `Presentation.ExportAsFixedFormat`을 COM 자동화로 호출하면
  인자 개수와 무관하게 `NullReferenceException`을 던진다. 수동 UI 실행("다른 이름으로
  저장 > PDF")은 정상 동작한다. 알려진 유형의 Office 자동화 버그로 보인다.
- 위 방법이 실패하면 `Presentation.SaveAs(path, ppSaveAsPDF)`로 대체한다. 이건 사람이
  누르는 "다른 이름으로 저장 > PDF"와 완전히 같은 코드 경로라 더 정확히 요구를 충족한다.
- 6개 중 1개(162슬라이드, 81MB)는 위 두 방법 모두 실패했고, 같은 포맷으로의
  `SaveCopyAs`(pptx → pptx)도 실패했다. 개별 슬라이드 `Slide.Export`(PNG)는 정상이었다.
  즉 렌더링 자체가 아니라 "패키지 전체를 다시 쓰는" 단계가 막힌 것이었다.
- 원인을 zip 내부까지 파고든 결과, 이 파일에는 이미지 250여 개 중 유일하게 TIFF
  파일(`image12.tiff`, 3.7MB, 3번째 슬라이드)이 있었다. TIFF만 PNG로 바꿔서 재시도해도
  여전히 실패해, 정확한 단일 원인을 완전히 특정하지는 못했다. TIFF/WDP(HD Photo)
  같은 비주류 이미지 포맷이 PowerPoint 저장 파이프라인을 막는 사례가 있다는 점만
  실측으로 확인했다.
- 위 세 방법이 모두 실패하는 파일을 그냥 실패로 남기지 않기 위해, 슬라이드를
  200DPI PNG로 렌더링해 새 프레젠테이션에 붙이고 그 새 프레젠테이션을 PDF로 저장하는
  방식(`Invoke-RasterFallback`)을 추가했다. 개별 슬라이드 렌더링은 대부분 살아있기
  때문에 이 방법은 거의 항상 성공한다. 텍스트가 이미지로 바뀌어 검색·선택은 안 되지만
  화면 모양은 원본과 같다. 이 방식으로 문제의 파일도 162페이지 PDF를 만들어냈다.

## 트레이드오프

- vector(1·2단계)와 raster(3단계) 결과물은 품질이 다르다(텍스트 레이어 유무). 스킬은
  결과 JSON의 `Method` 필드로 어떤 경로를 탔는지 알려주고, `raster`일 때는 사용자에게
  이 차이를 알리도록 SKILL.md에 명시했다.
- 폰트 임베딩 여부는 COM이 대신 처리해주지 않는다. pptx 내부 XML에서 실제 쓰인
  폰트와 `embeddedFontLst`, 시스템 설치 폰트를 대조해 사전에 경고하는 절차를 넣었다.
  처음에는 테마의 다국어 대체 폰트 표까지 포함해 오탐이 수십 개씩 났고, 슬라이드
  본문에서 실제로 쓰인 폰트만 보도록 좁혀서 해결했다.
- 매 파일마다 새 PowerPoint 프로세스를 열고 반드시 종료하되, 종료 지연에 6초의
  유예를 두어 정상 종료 중인 프로세스를 고아로 오판해 강제 종료하지 않게 했다.
