# 프로젝트 위키

검증되었거나 사용자가 수용한 장기 지식의 홈입니다. 독립적으로 반복 참조할
주제는 `wiki/` 아래 상세 페이지로 분리하고 이곳에서 연결합니다.

## 핵심 사실

- 기준 환경은 Claude Code이며 플러그인 하나, 작은 표준 라이브러리 런타임,
  조건부 스킬 열 개로 구성합니다.
- 사용자는 개발·기획·PM/PO·마케팅 사이의 실무 수준에 맞춘 자연스러운 한국어
  설명을 원합니다.
- 메일·Slack 지식은 사용자 발화뿐 아니라 광고주·인하우스·대행사 관점과
  원본 첨부를 함께 검토해야 합니다.

## 결정

- 기억은 `imports → 일일 로그 → NOW → 프로젝트 정본 → 전역 승격 후보 → 전역`
  순으로 검토·승격합니다. 전역 목적지는 프로필, 디자인 취향, 스킬 레퍼런스
  세 곳이고 서로 섞지 않습니다.
- 전역 승격은 자동으로 하지 않습니다. 후보를 `CANDIDATES.md`에 쌓고 게이트를
  통과한 것만 사용자 승인 뒤에 올립니다. 게이트는 사용자 명시 1회, 또는 관찰
  3회 이상과 프로젝트 2곳 이상과 최초·최근 간격 7일 이상입니다.
- 한 세션에서 세 번 본 것은 반복 관찰이 아닙니다. 게이트를 우회하려고 날짜나
  프로젝트 이름을 바꾸지 않습니다.
- 전역 파일은 줄 수 상한을 둡니다. 상한에 닿으면 승격 전에 먼저 정리합니다.
- 세션 시작에는 제한된 최신 문맥을 넣고, 매 턴에는 최신 로그 경로만 안내합니다.
- 전체 로그·imports·첨부를 자동으로 로드하지 않습니다.
- 질문·최종 답변·주요 도구 활동은 Stop 훅이 날짜·시간 순으로 자동 기록합니다.
- 원본은 Git과 기본 문맥에서 제외하고, 고객 식별정보 가능성이 있으면
  소유자 전용 권한으로 보관합니다.
- 반복 조사와 독립 축 비교는 최대 세 개 정도의 읽기 전용 서브에이전트에
  우선 위임합니다.
- Markdown을 지식의 유일한 정본으로 유지하고 SQLite FTS는 삭제 가능한
  검색 인덱스로만 사용합니다.
- 스킬 라우터는 일반 키워드 하나가 아니라 행동과 대상을 함께 확인하고,
  고신뢰 후보를 기본 최대 두 개까지만 제안합니다.
- 새 스킬은 번들·설치 목록을 먼저 확인하고, 외부 후보는 출처·리비전·권한·
  스크립트·라이선스를 검토한 뒤 승인된 범위에만 추가합니다.
- 라우팅 추천과 실제 Skill 호출 이름을 일일 로그에서 비교하되, 호출 관측치를
  정답으로 간주하거나 규칙을 자동 수정하지 않습니다.
- 프로젝트를 넘는 프로필과 디자인 취향의 정본은
  `~/.claude/personal-harness-data/global/` 한 곳만 사용합니다.
- 라우팅 품질은 실사용 발화를 라벨링한 시나리오 세트로 측정하고, 단위 테스트가
  만점을 요구합니다. 훅 관측치는 여전히 정답이 아니며 라벨만 정답입니다.
- 스킬 집행 품질은 하네스 자체의 품질 게이트에서 뽑은 루브릭으로 채점하고,
  집행에서 새로 발견한 판단 규칙만 방법론으로 승격합니다.
- 배포되는 플러그인 내용은 `plugin/` 아래에만 둡니다. 플러그인 설치는 소스
  디렉터리를 예외 없이 복사하므로, 프로젝트 상태와 제한 원본이 소스에 있으면
  그대로 캐시로 유출됩니다.
- 사용자가 외워야 하는 명령은 만들지 않습니다. 훅이 기본 동작을 담당하고,
  유지보수는 `./harness status` 하나와 슬래시 명령으로만 노출합니다.
- 독립적인 축은 한 메시지에서 동시에 서브에이전트로 띄우고, 각 에이전트가 쓸
  파일을 미리 지정해 충돌을 막습니다.
- `imports` 보존은 4계층입니다. 조사 요약은 영구, 집계 원본은 프로젝트 종료 +
  월간 마감 1회, 개인 단위 데이터는 집계로 대체하는 즉시 삭제합니다. 계층 표는
  `.harness/imports/RETENTION.md` 한 곳에만 두고 런타임이 기한을 감시합니다.
- 원본을 삭제하기 전에 그 원본을 근거로 삼은 요약이 무엇인지 확인하고, 해시는
  남겨 같은 파일을 다시 받았을 때 대조할 수 있게 합니다.
- 배포 이름은 npm 패키지, 플러그인 매니페스트, 마켓플레이스 항목에서 하나로
  유지하고 테스트가 일치를 검사합니다.
- 배포 경로는 Claude Team 조직 설정입니다. 조직 sync는 배포 시 플러그인을
  패키징하므로 팀원은 저장소 접근 권한이 필요 없고, 도메인·npm·공개 저장소가
  모두 불필요합니다.
- 조직 배포는 `npm` 소스를 지원하지 않고 마켓플레이스 저장소가 private 또는
  internal이어야 합니다. 비공개 플러그인은 저장소 안 상대 경로로 참조합니다.
- 플러그인 id는 소문자·하이픈·64자 규칙을 따릅니다. 대문자 브랜드 표기는 id가
  아니라 `displayName`에 둡니다.
- 사람이 읽는 설명과 모델이 라우팅에 쓰는 설명은 모두 한국어를 기본으로 하고,
  영어 발화도 매칭되도록 영어 트리거 용어를 목록에 함께 남깁니다.
- 한국어에서 `—` 줄표, 번역투, 과공대, 상투구, 질문 칭찬은 금지입니다. 이 규칙은
  UI 문구뿐 아니라 하네스 자신의 답변에도 적용하고 테스트로 검사합니다.
- 화면 안 문구, 산문, 레이아웃은 서로 다른 스킬이 담당합니다. 문구를 레이아웃
  작업 안에서 즉석으로 쓰지 않습니다.
- 한국어 설명은 영어보다 토큰이 비쌉니다. 상시 비용은 실측으로 관리합니다.
- 전역 프로필 템플릿에는 특정 사용자의 역할·선호를 사실로 넣지 않습니다.
  팀 배포에서 다른 사람의 기본값이 되기 때문입니다.
- URL로 추가한 마켓플레이스는 `marketplace.json` 한 파일만 내려받으므로 그
  경로를 쓸 때만 `github`·`git-subdir`·`npm` 소스가 필요합니다.
- 자격증명은 받지 않습니다. 조직 설정과 계정 작업은 소유자가 직접 수행하고,
  하네스는 파일과 절차만 준비합니다.

## 용어

- 정본: 현재 프로젝트에서 재사용할 검증된 사실·결정의 단일 위치
- imports: 메일·Slack·첨부의 제한 원본과 재검증용 조사 요약
- MOC: 상세 위키 페이지의 위치와 관계를 보여 주는 짧은 홈·목차
- restatement: 후속 보고서에서 과거 수치가 재조정되는 현상
- 측정 계약: 기간, 목적, 비용, 전환, 출처, 귀속, 갱신, 사업 KPI의 합의
- 후행 품질: 가입·구매 뒤 응시, 활성, 가동, 재구매처럼 실제 가치에 가까운 결과

## 검증된 패턴과 교훈

- 매체 효율과 1st-party 사업 결과를 별도 열로 유지하고 후행 품질까지 연결합니다.
- 조회·트래픽·전환 목적은 예산과 스코어카드를 분리합니다.
- 작은 표본의 좋은 효율은 확장 결론이 아니라 다음 검증 후보입니다.
- 같은 사용자 코호트인지 확인하지 않은 독립 이벤트 합계로 퍼널 전환율을
  만들지 않습니다.
- 파일명보다 실제 포함 기간, 비용 기준, 전환 정의, as-of 시각, 외부 링크,
  피벗 범위와 수식 오류를 먼저 확인합니다.
- 당월본과 후속 역사표의 수치가 다르면 버전과 공식 마감값을 기록합니다.
- 클라이언트별 수치·매체 우열은 시점성 사실로 imports에 남기고 전역 규칙과
  분리합니다.
- 정밀도 우선 라우터에서 recall 실패의 대부분은 점수식이 아니라 어휘 커버리지
  문제입니다. 일반 대상어와 도메인 고유 신호를 구분해야 임계값이 작동합니다.
- 하나의 신호가 자기 자신을 보강하지 않도록 강신호에 포함된 행동어·대상어는
  별개 증거로 세지 않습니다. 증거가 늘면 점수는 내려가지 않아야 합니다.
- 리포트가 계산해 준 파생 지표(진행률·소진율·달성률)는 분모부터 검증합니다.
  실제 원본에서 분모 하드코딩과 `#REF!` 파손을 확인했습니다.

## 열려 있는 질문

- 프로젝트별 실제 사용에서 어느 스킬이 과도하거나 부족하게 트리거되는가?
- 사용자의 전역 디자인 취향은 어떤 실제 선택에서 반복 확인되는가?
- 제한 원본의 보존·삭제 주기를 어떤 회사 정책에 맞출 것인가?

## 분리 기준

- 이 파일이 500줄을 넘어 탐색이 느려짐
- 한 주제가 독립적으로 반복 참조됨
- 주제마다 담당자나 변경 주기가 다름

분리한 뒤에는 원문을 중복하지 않고 이 색인에 링크와 한 줄 설명을 남깁니다.
